This system uses the Enterprise Web Library (EWL), an opinionated .NET framework for enterprise web applications. These shared rules supplement the system's own `AGENTS.md`; use that file and the actual project configuration for system-specific paths and conventions.

## Development Modes

Standard mode is the default. `/adhoc` selects ad hoc mode for the current session; `/standard` restores standard mode. Keep the selected mode across requests until changed, including in session summaries. These commands select the workflow below rather than overriding unrelated rules.

| Activity | Standard | Ad hoc |
|---|---|---|
| Pre-edit formatting and formatting-only commit | Follow the workflow below | Skip |
| Abstraction-review and cleanup subagents | Follow the workflow below | Skip |
| Running-application preflight, application startup, runtime verification | When relevant to the task | Only when explicitly requested |
| Generation, builds, and non-runtime verification | As needed for the change | As needed for the change |

Do not perform skipped formatting or review workflows manually as a substitute. Explicit user instructions may waive verification or request a particular check without changing the session mode. Source ownership, code conventions, and preservation of existing work apply in both modes.

## Standard Development Workflow

This formatting and review workflow applies only in standard mode. Use the current harness's subagent tool.

1. Before the first functional edit to each clean, existing C# or XML/XSD file in a task, invoke `ewl-cleanup` to format only, not inspect, and commit any formatting changes. This authorizes formatting-only commits of those files. Skip this pre-edit step for new or already-modified files; preserve existing work and continue. Do not repeat it for subsequent edits or attempt it retrospectively when returning from ad hoc mode.
2. Make the requested changes and regenerate affected output when required below.
3. After functional C# changes, invoke `ewl-abstraction-review` on the changed, non-generated C# files. Address applicable findings.
4. Invoke `ewl-cleanup` to format and inspect, without committing, only the changed non-generated `.cs`, `.xml`, and `.xsd` files. Exclude other file types and C# files containing `<auto-generated`. Include new and previously modified files. Reported fixes are already applied; address only remaining issues.
5. Verify the final code, including relevant inspection fixes, with generation, builds, and tests appropriate to the change. Honor explicit user instructions to omit verification and report what was not run.

In standard mode, check for relevant running applications when needed before an operation that overwrites their binaries. If an application blocks the operation, identify it and ask the user to stop it; continue independent work. Do not check every output before unrelated work or interpret every file-access failure as an application lock.

## Build, Generation, and Tests

Find the actual solution and test projects before running commands. The names below are placeholders; NUnit, a `Tests` project, and its exclusion from Release are common conventions, not guaranteed system properties.

```shell
dotnet restore "Solution Name.sln"
dotnet build "Solution Name.sln"
dotnet build "Solution Name.sln" -c Release
dotnet test "Tests\Tests.csproj" -c Debug
dotnet test "Tests\Tests.csproj" -c Debug --filter "FullyQualifiedName~Tests.SomeClass.SomeTest"
```

The Development Utility (DU) generates code in `Generated Code\` folders; builds do not run it automatically. After changing generation inputs such as schema, page declarations, or configuration, run `sync`, build, and inspect the relevant generated output unless the user explicitly waives these steps. From the solution directory:

```shell
dotnet tool restore
dotnet ewl sync
```

Restore tools only when needed. Use the system's installed DU for normal development. To consume changes made in the EWL source repository, first update to a DU package containing them, or use the local DU/local-package workflow for development. An existing packaged DU does not automatically consume another checkout's edits.

## Source Ownership and Tools

- Preserve existing work. If a `.hg` directory is present, load `ewl-mercurial` before version-control commands and use Mercurial. Otherwise determine the actual VCS rather than assuming Git.
- **Edit sources, not generated output.** Do not edit `Generated Code\`, `.ewlt.cs`, or other files marked as generated. Reading generated output is encouraged when needed to understand or verify behavior.
- Prefer dedicated tools for file reads, searches, and edits. Use `ewl-powershell` for PowerShell commands; do not invoke PowerShell through another shell tool. Follow the actual shell tool's description and quote paths containing spaces or non-ASCII characters.

## Project Organization

- **`Library`**: shared business logic, configuration, data access, and providers; normally references EWL and optional provider NuGet packages.
- **`Website`** or other web projects: page classes and UI logic, referencing Library.
- **`Solution Files`**: solution-level build configuration and scripts.
- Configuration uses XML validated against XSD schemas under `Configuration\`.
- UI uses EWL's C# component model, not Razor. Page classes use generated URL routing; database access uses EWL's generated data-access layer.

## Code Style

Follow surrounding code and system-specific conventions, with these EWL defaults:

| Element | Convention | Example |
|---|---|---|
| Namespaces | PascalCase matching directories | `MySystem.Library.DataAccess` |
| Classes and interfaces | PascalCase | `OrganizationSpecifier` |
| Public/internal methods | PascalCase | `GetRows()` |
| Private methods | camelCase | `getContent()` |
| Internal readonly fields | PascalCase | `Host` |
| Private fields, locals, parameters | camelCase | `organizationId` |
| Private constants | camelCase | `tickInterval` |

- File-scoped namespaces; `using` directives at the top, System first, then other namespaces alphabetically, without blank lines between groups.
- Tabs for indentation. Spaces inside parentheses and attribute brackets: `( value )`, `[ Test ]`. No spaces inside generic angle brackets: `Func<Instant>`.
- Opening braces on the declaration line. Prefer expression-bodied members for single expressions.
- Preserve non-ASCII typography in prose; do not convert curly quotes to straight quotes. Use the typography tool when needed, and preserve code syntax and literal data.
- Strings should be nullable only when `null` means something distinct from empty. Optional string parameters normally default to `""`.
- Prefer applicable EWL/TEWL helpers such as `.ToCollection()`, `.Materialize()`, and `.ToComponents()`. Consult the abstraction inventory when implementing utility-like behavior; do not replace existing helpers with manual equivalents.
- Use `DataModificationException` for user-correctable data errors; follow surrounding usage of `UserCorrectableException` and `UnexpectedValueException` for other errors.
- Follow the system's schema and established primary-key convention; EWL systems commonly allocate IDs with `MainSequence.GetNextValue()`.
